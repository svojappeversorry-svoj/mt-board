# iOS via Capacitor — project structure and what's left

This is the Capacitor path from `docs/IOS_READINESS.md`: `index.html` runs almost unmodified
inside a native WebView, rather than being rewritten in Swift. This session set up everything
that can be set up **without macOS/Xcode** (this sandbox is Linux — no `xcodebuild`, no
CocoaPods). The generated Xcode project needs a Mac to actually open, build, sign, and submit.

## What's in the repo now

- **`package.json`** — hosts the Capacitor tooling only. The app itself is still the single
  `index.html` file; nothing about how it's written changed.
- **`capacitor.config.json`** — `{ appId: "com.svoj.app", appName: "SVOJ", webDir: "www" }`.
- **`www/index.html`** — a copy of the root `index.html`. This is Capacitor's "web asset
  directory" — it can't point `webDir` at the repo root directly, because then `docs/`,
  `scripts/`, `.git/`, etc. would all get bundled into the app too. **`www/index.html` is a
  build artifact of the real source of truth (the root `index.html`), not a second copy to edit
  by hand.**
- **`ios/`** — a full native Xcode project (`ios/App/App.xcodeproj`), generated by
  `npx cap add ios`. Uses Swift Package Manager for Capacitor's plugins (`CapApp-SPM/`), not
  CocoaPods — no `pod install` step needed, which is exactly why this could be generated from
  Linux. `ios/.gitignore` (generated alongside it) already excludes build output, `DerivedData`,
  and the copied `App/App/public` web assets.
- **Bundle identifier:** `com.svoj.app` (your choice — this needs to match what you register in
  App Store Connect later; changeable in Xcode's project settings before that matters, but not
  worth changing after you've created the App Store Connect record).

## The one workflow rule: never hand-edit `www/index.html`

Always edit the root `index.html`, then run:

```sh
npm run cap:sync
```

This copies the root `index.html` into `www/index.html` (`npm run build:web`), then runs
`cap sync ios`, which copies `www/` into `ios/App/App/public` and refreshes the native project's
plugin list. Do this after every change to `index.html`, before opening/building in Xcode —
otherwise Xcode is building against a stale copy.

## What you need on your Mac to actually build this

1. **Xcode** (from the App Store — free), plus its command-line tools.
2. **An Apple Developer account.** A free account is enough to build and run on the Simulator or
   your own device. **A paid Apple Developer Program membership ($99/year) is required** before
   you can use TestFlight or submit to the App Store — you'll need this before real submission,
   not before local testing.
3. Clone this repo, then from its root:
   ```sh
   npm install
   npm run cap:sync
   npx cap open ios
   ```
   The last command opens `ios/App/App.xcodeproj` in Xcode directly (no `.xcworkspace` — this
   project doesn't use CocoaPods).
4. In Xcode: select the **App** target → **Signing & Capabilities** → pick your Apple Developer
   Team. Xcode will offer to create a provisioning profile automatically the first time.
5. Pick a Simulator (or your connected iPhone) from the scheme selector and hit **Run**. The app
   should launch showing SVOJ's real sign-in screen — it's the exact same `index.html`, running
   inside a `WKWebView`, talking to the same PROD Supabase project the Web app uses today (see
   "Which Supabase project it talks to" below).

## What's still genuinely missing (all from `docs/IOS_READINESS.md`, none of it started)

None of this blocks opening/running the app for the first time — these matter once you get to
specific features or to real App Store submission:

- **App icon and launch screen.** `ios/App/App/Assets.xcassets` currently has Capacitor's blank
  placeholder icon/splash slots. A real icon set (multiple resolutions) and launch screen need to
  be designed and dropped in before submission — App Store Connect will reject a placeholder icon.
- **Permission strings in `Info.plist`.** Nothing has been added yet. The plain
  `<input type="file" accept="image/*">` photo picker Journal/My Day already use tends to work
  via the modern `PHPickerViewController` sheet without needing
  `NSPhotoLibraryUsageDescription` (Apple's photo picker mediates access so the app never directly
  touches the library) — worth confirming once you can actually test on a device, since this is
  the kind of thing that behaves differently in a real WebView than in Safari. If you add
  `@capacitor/camera` for a native camera capture button, or `@capacitor-community/health` for
  Steps, those *do* require their own usage-description strings (`NSCameraUsageDescription`,
  `NSHealthShareUsageDescription`) — add them when you add the plugin, not before.
- **"Export SVOJ" (Settings) needs a plugin.** It currently builds a `Blob` and triggers
  `<a download>`, which is browser-only and unreliable inside a WebView. Needs
  `@capacitor/filesystem` + `@capacitor/share` wired in, or it should be hidden/disabled on the
  iOS build until that's done — flagged in `docs/IOS_READINESS.md`, not started here.
- **Steps/HealthKit.** Architecturally ready (`STEPS_SOURCE`/`window.SVOJ_NATIVE_HEALTH` — see
  `docs/IOS_READINESS.md`), but no real HealthKit plugin is wired in yet. The widget correctly
  shows "not available on web" until it is.
- **Push/local notifications.** The three Settings toggles (`wp-notif-prefs-v1`) still only save
  a preference — no `@capacitor/local-notifications` or `@capacitor/push-notifications` wired up,
  no actual scheduling/delivery code exists yet.
- **DEV vs PROD Supabase switching.** `index.html`'s `SUPABASE_URL`/`SUPABASE_ANON_KEY` are still
  hardcoded to PROD (see below) — there's no build-time config yet to point a debug build at DEV
  instead. Deliberately deferred; ask for this specifically when you want it.

## Which Supabase project it talks to

**Still PROD** (`https://cdvvpkpbqkxxyytphjht.supabase.co`) — `index.html`'s hardcoded constants
were not changed by this setup, so the app you just built and ran talks to the exact same backend
the live Web app uses, real user accounts included. The DEV project
(`https://gtwbkixtadfevajhaylt.supabase.co`, see `docs/SUPABASE_ENVIRONMENTS.md`) exists and is
ready, but nothing points at it yet — that requires making the Supabase URL/key configurable per
build, which was deliberately left for a separate, explicit task so this session didn't touch
`index.html`'s Supabase config while also standing up the iOS project. **Be aware of this before
doing throwaway testing on your device** — signing up a test account or writing junk data through
the iOS build right now lands in the real PROD database, not an isolated one.
